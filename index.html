Circular Game Simulator

Gaming
Status
In Progress
Year
2026
Tools & Hardware
PCB Design, Kicad, 3D Printing, Fusion 360, Cura, 3D Printed Circuit Board, RP 2040, MicroPython, SPI, Soldering
Why:


This handheld game simulator was an excuse to create a 3D printed circuit board from a video seen online, to explore the world of PCB Design.

I had a few thumbsticks lying around from taking apart an old MOGA Gaming Controller for an iPhone. I also had some circular OLED displays lying around that I though would work well for this project.



How:


I took inspiration from one of the small handheld retro games consoles I have seen online. I used a 1.28" Circular OLED Display with a GC9A01 IC that I had lying around as the focus point for this project.

I quickly got to grips with how the GC9A01 chip worked with a microcontroller and connected using SPI to run a quick test that I could display a dot in the middle of the screen and that I could change the colour of that dot with a button to show the display changing. Next I connected the MOGA Thumbstick and read in the X and Y values and used that to move the dot around the screen.

Once I had all of the basic components working I went to KiCad to create a circuit schematic on there, connecting all of the relevent pins on the microcontroller to the components. I then turned the schematic into a PCB layout, having to create a few components and download a few more from the internet. Once my sinle layer PCB design was done. I was able to export this into Fusion 360, then extrude all of the traces up slightly.

Once I had the 3D printable STL file ready I printed this off, once printed I placed it down and applied the thin copper tape to the whole top layer over the extruded traces. With this in place and covering the whole PCB I used a very sharp knife to cut downt he sides of each of the extruded traces, creating a thin copper layer on each of the extruded traces only. Then I poked holes where all of the components were going, using the end of a pair of tweesers.

Once all holes were created I placed all of the components in one by one and soldered them down to the copper traces. I then soldered wires across the last few components to connect ground. After diagnosing a few dodgy connections, the whole PCB was working and I then created a case to house the PCB and the hardware was completed.

Using Claude I quickly created a set of 3 games to use on the device, Pong, Maze and Brickbreaker. These games are very quick prototypes and I am still working on optimising them to work perfectly.



What I learned:


The largest thing I learnt on this project was KiCad and creating PCB layouts. During this I learnt how to create a schematic on KiCad, how to ensure I had through-hole components selected, creating compononets in KiCad ensuring I had the correct dimensions, the importanace of trace width, downloading Gerber files and importing into Fusion 360.

Outside of KiCad I also enforced my knowledge on SPI and communicating to graphical displays, ensuring I connect to the correct MOSI and MISO pins on the microcontroller.



What to improve for next time:


As this project is still ongoing, there is still plenty of work to be done on the software, so I will update on that at a later date.

In terms of Hardware, I was quite happy with most of it came out, I would like to redo the casing to get that to fit perfectly around the circular display, I had issues getting perfect measurements on that and its posisiton, leading to a bunch of soldering needed to be done.
As well as this I would like to work on making the PCB event more compact and pusht that to its limits as it just feels slightly too big.

SRT Monitor

Software
Status
Complete
Year
2025
Tools & Hardware
VS Code, Python, Tkinter, Magewell API
Why:


While using the Magewell Ultra Encode SDI, I wanted a way to track key metrics of the stream coming from the senders side and log them into graphs over time.
This will allow the sender to ensure the stream is being sent out of their network stably to help find the route cause of connection issues.

How:


The majority of the Tkinter layouts, lables, app design, was done by me in Python, using Youtube videos, code I had already written and examples I had read online.
Then the bulk of the code to connect to the encoders API and pull the data and store it was done using Claude Code.

To start I created a very basic Tkinter window with a few labels to show the IP address of the encoder that was hardcoded in at this point. As well as a few small pieces of data available from the API such as CPU temp and the name of the stream and the bitrate it was outputting.

Using Claude to help me log in to the encoder and pull the data I wanted from the API, I stored this in a json file that I then read from and displayed on labels in the Tkinter window.

Once I had the basic function of connecting to an encoder and pulling the data in it was a fairly simple job of going through the API data sheet from Magewell and deciding what data I wanted to collect. This all then got placed in a list in a JSON file and then for the data that was just a text variable that constantly updated to show the latest value on the label that check over every second or so.

Then I had worked on placing all of the labels around on the window to create a good looking app with information clustered together nicely.

The next big task was the main graph, this would display the historical data over adjustable periods fo time ranging from 1 min to 12 hours. I took some code from my Spherical Parallel Manipulator project I worked on while at University that pulled in servo positions and logged them in a graph.

Using this I was able to create the basic graph with Axes and labels using the Matplotlib library, then with a bit of tweaking and help from Claude I got it to start plotting a line for the bitrate of a stream on an encoder, updating once a second.

Then I expanded the graph to have 4 different lines being plotted for Bitrate, TTL, Buffer and Target Bitrate, all customisable to be able to display them or not at the tick of a button. By doing this I introduced extra units of measure as Bitrate and Target bitrate was in Mbps where as TTL and buffere was in milliseconds, so I had to add in an extra Y axis on the far side to display that data corretly.

Then once this worked the core functionality was all there and I had to add in some minor cosmetic tweaks such as an adjustable slider for the Y axis, adjustable X axis measurements from 1 min up to 12 hours, and text changing colour based on changes in the encoder.

Once all of these were done I implemented a home screen that allowed you to input the Username, Password and IP address of the encoder you were trying to connect to as it was still currently hardcoded to the test encoder, once this worked and the encoder log in pulled the entry field values, some error messages were added to the log in screen to tell you if there were errors logging in connecting to the encoder.

I then converted it all into a single exe file with custom logos on the toolbar and app and sent it out to be used by the team.

What I learned:


During this build the main area I learnt about was API requests. I had to learn how to connect to the Magewell Encoders and use GET requests to pull the data in.

On top of this I continued to keep learning Python and Tkinter for making GUIs. Work that had been started during the Spherical Parallel Manipulator Project. A lot of the graphing and Tkinter code was taken from that project and reused here as there were a lot of similarities.

What to improve for next time:


Currently I am wokring alongside another coworker to create a similar application that is a more fit for purpose solution for our needs at work, taking in a lot of the data collected from this app and placing it in the new app.

In terms of functionality in this app, it works fairly well, with no major blips, however due to the limitations of Tkinter there is only so much that can be done to improve the look of the app. It looks very outdated and could do with a makeover. To do this I would look at using something like CustomTkinter as a start to improve the look of it.

In future I would then probably look at upgrading this app to use C++ for a more professional look, better performance and more features.

Remote Pinger

Networking
Status
Complete
Year
2025
Tools & Hardware
Waveshare RP2040-ETH, VS Code, TP4056, 3D Printing, Fusion 360, Cura


Why:


In my work I do a lot of networking tasks and needed a simple way to test connectivity from remote locations. Previously I would have to plug a laptop into the network and leave it in a remote location often outdoors in the elements. This was far from ideal, so I started looking at making a smaller programable on the fly device that would let me alter the devices IP.



How:


I used a Waveshare RP2040-ETH board that I had lying around. This board has a RJ45 port integrated onto the board already with a built in Ethernet controller, simplifying the build massively. The basic design was the RP2040 board being powered from a TP4056 battery module, with a 400mAh battery. Then there were an assortment of buttons and a screen to display the IP and control the UI.

I used a 0.28 inch OLED display powered from the RP2040 to create and interactive UI. This used a simple I2C connection to display the how the device was currently configured. Then using a maze of if and else statements I was able to create a mini display with a Home Screen, set IP Screen and set Subnet Screen.

Using a piece of Perma Proto Board, I added 4 buttons in an up, down, left and right configuration, as well as 2 more as OK and Home buttons. The OLED Screen was connected to this board, as was an on and off switch.

After wiring up all of the buttons to the RP2040, the battery to the TP4056 and the OLED to the RP2040, I designed the housing for all of this in Fusion 360. The design was made in 3 parts, the botton, the main body and the top cover. The bottom has a large square hole to store the battery as well as a square hole in the side plate for the RJ45 connector to poke through. The Main body case has holes for the USB C ports for the TP4056 charging port and the USBC port for the RP2040 for reprogramming in future. The top cover then has holes for the screen to poke through as well as so buttons can added and protude through the top of the cover to make them easier to press.

The buttons were then just 3D Printed as small cylinders with large bases that could poke through the top cover from below and sit nicely on top of the buttons so they pressed nicely and didn't come off. After a bit of sanding and filing, everything fit in place ok and then threaded inserts were added to pieces to allow all 3 of the pieces to be screwed together nicely.



What I learned:


During this build I learnt about I2C displays and how to interface with them. A lot of this was me trying to figure out how to create an interface with multiple pages and how to navigate them with minimal buttons. I used a large combination of if and else statements to get this display to work as I hoped. This method worked ok for my small display with only a handful of buttons and pages for the display. However scaling this up would be abit of a nightmare to manage. So in future for larger projects I will look to find another method to do this.

I also learnt about buttons and how they will often bounce when in a system like this and the need for a debouncing system to avoid false readings. For my system I used polling delays and edge detection latches to catch any bouncing or double presses to avoing an annoying user experience.



What to improve for next time:


There are a few features and changes that I would make for the next iteration:
1. I would use a different MCU board or a separate Ethernet controller. This is because the RP2040-ETH has a maximum connection speed of 10Mbps. A lot of 10G switches that I have used will not connect to a 10Mbps connection. Therefore looking at upgrading this speed to 100Mbps would allow me to connect to all switches I currently use with no issue. Better yet a 1Gbps Ethernet controller would allow me to ensure all cable connections to the end devices we use are running at 1Gbps as this is a common issue I see, with cables being run that only work at 100Mbps.

- 100Mb Connection speed
- Device that can ping as well as be pinged
- Improve 3D prints to fit flush without Blue Tack filler
- Use 1 USBC port instead of 2

Lipo Charger

Electronics
Status
Complete
Year
2025
Tools & Hardware
TP4056, 3D Printing, Fusion 360, Cura
Why:


When recycling old lithium-ion batteries from old devices I had lying around I had an issue that I had nothing to charge each of these batteries with.
I had multiple TP4056 modules lying around from a previous bulk order, allowing me to use a USB Cable to charge all of my reclaimed batteries.

How:


With the circuit being so simple, there was no need for a real test as I have used these modules in other projects before. All that was needed was a 3D design for the housing of the board as well as figuring out a way to easily connect and disconnect the assorted batteries from the board. I had a box of screw in connector blocks lying around which would provide me with an easy way to screw in the exposed wires of the batteries or connect jumper wires into battery connectors to the board.

With the dimensions of the connector block taken, I designed a 3D model of a casing in Fusion 360 and printed it out on my Ender 3 Pro 3D Printer. The design was made to ensure the connector block would just press fit in and stay in place.

The design was made out of white PLA filament allowing the charing and fully charged lights to shine through the print

Wires were then soldered from the legs of the connector block to the B+ and B- pads on the TP4056. After a quick check and seeing all the pieces work and the batteries were charging correctly I put it in the casing and with a little bit of shaving down pieces I got it all to fit in and labeled the pins of the connector block with + and -.

What I learned:


During this project I learnt about 3D printing tolerances and how to get something to press fit and what gaps I needed to leave to get a tight fit on my 3D printer.

Aswell as this I learnt about how small a gap I can leave before the print gets too thin and breaks, this was seen when making the top casing of the 3D print, this cracked as the rails were too thin.

What to improve for next time:


Next time I would improve the design of the top of the casing and the rails to have thicker plastic as in this version they cracked and did not fit in perfectly and required a lot of filing to make them slot in nicely.
Aswell as this I would like to integrate in a standard 2.0mm JST-PH connector to the board to allow me to plug these lipos I use in my small projects directly in without having extension cables or to cut and strip the ends.

Spherical Parallel Manipulator

Robotics
Status
Complete
Year
2021
Tools & Hardware
3D Printing, Raspberry Pi, Servos, MicroPython, Tkinter
Why:


This project was done as my final year engineering project while at University. The goal of this project was to solve a real world problem in the live officiating of tennis where cameras used down by the court that look down the service T and baselines to check for foot faults, are regularly knocked out of position whether by balls, ballboys, players or other officials on the court. The remote operation of tennis often makes it difficult to be able to go courtside to fix all of these knocked cameras across up to 20 courts.

To solve this issue, as all courts have a network connection to these IP cameras, using a small device that can be remotely controlled over IP to pan an tilt back into position.

Due to the University needing this to be more complicated than a simple pan and tilt system, the system was altered to include a roll axis, and therefore the Spherical Parallel Maniputlator design was chosen.

How:


The system was made up of 3 main components, The mechanical Spherical Parallel Manipulator design, the RaspberryPi to power and control the system as well as to connect to over VNC to access the control app, and the control app itself coded in Python using Tkinter.

Mechanical System

A spherical parallel manipulator system was found on Thingiverse by a designer named plusalphaDesigns. This was then remixed from their design to fit my needs.

The Spherical Parallel Manipulator has 3 central gears that spin independently to control each arm, a base plate that could hold a cetnral pin for these gears as well as mountings for each of the 9g servos was designed using solid works and 3D printed. Along with the central gears, arms and pins that were taken from plusalphaDesigns model.

Following this a driver gear had to be attached to the servos to drive the central gears with enough of a gear ratio to provide the torque to drive the central gears. This again was created using SolidWorks and then 3D printed and attatched to the top of a shaved down servo horn.

Raspberry Pi System

I wanted the Raspberry Pi to sit in a remote location and be accessed via VNC. So after booting up the Pi and installing Debian, I installed VNC to the Pi and set a static IP fon it. I was then able to plug it into a network switch and access it over the network from my PC for remote control.

Control App

To control the SPM, I used a MicroPython app to send commands to the servos to move them around. I used Tkinter to create a GUI that I could press buttons on to move the servos a little bit at a time to make the SPM move up, down, left right and tilt in each direction.

What I learned:


A larger part of this project was improving my CAD skills, I had to take an original build and modify the parts I needed to work differently including the base, camera holder at the top and gears.
This was also the first project where I used a Raspberry Pi. The Pi 4 required a lot of learning about linux and debian distros and how to set up and operate them.
Along side this it was my first time using MicroPython and the Thonny IDE. This took some getting used to and how to interact with GPIO pins and the board itself.

Inside MicroPython I had to build out my first proper Tkinter GUI outside of little calculators and password entry pages. Creating a fully funtional GUI with updating labels, buttons that sent actions to the servos and Matplotlib graphs to read in and display the servo positions over time.

What to improve for next time:


There are a number of things I would improve for next time:

I would improve the connection between the teeth of the gears connected to the servos and the central shafts. There was a lot of backlash on these teeth and did not connect together very easily. Causing teeth to often become misaligned and snag, which caused the system to stop spinning.

I would also like to work on the speed at which the motors spin, I had the servos turing at full speed all of the time which caused the camera to look quite jerky when moving around, not giving the best image. On top of this solidifying the backlash in the teeth and securing the joints better, potentially using bearings would allow for much smoother movements.

I would like to work on minimsing the connections needed for the board. I would like to create a housing to store the Raspberry Pi and see if I can reduce the board itself and use something like a pico to fit in the smaller form factor and instead of running a Tkinter app I would sun some kind of Http server using an ethernet controller board that you could connect using a configurable IP address.

In trying to make the design smaller I would like to power it over POE, I would probably use a POE splitter to detatch the power from the data connection. There would likely need to be alot of work done on power and how much is needed and how much a POE switch can deliver and potentially would need to look at other designs or motors, but I imagine it could be done.


This Spherical Parallel Manipulator was originally printed with all of the parts from the original model by plusalphaDesigns (See the second last photo). From there changes and alterations were made to improve the build to make it more efficient and suited to my needs, as well as a whole new control system using a Raspberry Pi.

What was kept the same:

The central gears and all three sets of links were kept the same from the initial build, as no real big changes could be made for these parts without massively changing the designs to put in bearings to help reduce friction.

As well as this all of the pins were kept the same.

These parts from the original plusalphaDesign build were:

- Gear Level 1
- Gear Level 2
- Gear Level 3
- 90deg Link : 3ea
- Link Level 1
- Link Level 2
- Link Level 3
- Link Pin : 3ea
- Stack Pin
- Stage Pin : 3ea

Changes

The main mechanical changes in the new build were:

The use of Nylock nuts to stop the nuts on the joints coming loose that seemed to happen often.

The Top Stage was redesigned by measuring the 3D print and 3D modelling one exactly the same size as it to allow it to fit onto the original links. Then a cut was made into it the same size as the camera used in the build to allow it to sit in nicely, with a hole in the bottom to allow the camera to be screwed in. The camera used can be found here.

Amazon Link to Camera


The original build had a 1:1 gear ratio, in this build this was changed to a 2:1 ratio to improve the torque in the system and allow it to comfortably carry more load. By keeping the central gears the same size and then reducing the diameter of the servo gears from the original 40mm down to 20mm this gear ratio was achieved.

With the newly designed base, this made room for some more changes. The large triangular base made the design more sturdy and unlikely to tip, as well as allowing for an arrow on one corner to be made to show which way the base and the system should face. With the new smaller servo gears, the servo mount brackets had to be moved closer to the central gear shaft to allow for this smaller diameter. Some calibration markers also were added, this allowed the servo gears to be set at a zero point and then give an easy visual aid as to where the gear has moved.

As well as this, all links that touched eachother had metal washers added to them and were sanded down to try and reduce friction and make the system as smooth as possible

Certain parts such as the motor brackets and gears heights were slightly lowered to make the gears all line up more flush to stop any gears getting caught.

Electronics

All of the electronics were controlled by a Raspberry Pi 4, however a Raspberry Pi 2 or 3 should work perfectly fine for this purpose. The 3 servos were powered from an external power supply. An app on Tkinter was created to control the servos directions and movements as well as relay back real time data on the servo positions. To get this data back into the RPI, an MCP3008 ADC was used to convert the signal from the analog feedback pin of the servo to a digital signal for the RPI to take in. This data was then presented in number format as well as graphically for each servo.
